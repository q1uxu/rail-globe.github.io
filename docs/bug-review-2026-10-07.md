# CNRail bug review

Review 日期：2026-10-07。对象是 `main` 分支当前工作区，包括尚未提交的修改。没有修改业务代码、重建生产数据、提交或推送。

结论：发现 9 项可定位的问题，其中 1 项 P1、8 项 P2。最需要优先修复的是寻路图中的跨线路连接规则。

P1 表示核心结果可能错误，应优先修复。P2 表示特定操作或数据条件下产生错误结果、功能失效或数据损失。

## 1. [P1] 普通轨道节点允许跨地铁线路免费换乘

位置：`scripts/build_graph.py:190-200`，相关切分逻辑为 `127-142`。

`nid()` 只以坐标编码作为节点身份，不区分线路。不同线路在相同坐标上的边接入同一个节点，前端 Dijkstra 可以直接从一条线路进入另一条线路。这个过程不经过车站 hub，所以绕过了换乘成本和换乘提示。

现有 `graph.json` 复现：上海的“上海体育馆 → 上海火车站”路径为：

1. 上海地铁4号线，35 米。
2. 上海地铁1号线，5,327 米。
3. 上海地铁13号线，3,170 米。
4. 上海地铁1号线，726 米。

中间这些线路切换全部发生在轨道节点，没有 `y` 换乘边。原始算法总成本约 21.43 分钟，扣除首尾 hub 成本后显示约 15 分钟。这里的问题不依赖具体车次或时刻表：不同地铁线路的旅客换乘不应绕过车站模型。

现有图里共有 439 个非 hub 节点接入至少两条地铁线路。这个数字是影响面线索，不表示每个节点都应完全断开。

建议：把物理轨道连通性和旅客线路状态分开。地铁线路之间只通过明确的换乘站连接，保留线路状态及换乘成本。铁路道岔的物理贯通不能一刀切删除，但需要与旅客换乘规则区分。提取阶段保留 OSM node 身份及必要的层级信息，避免仅凭坐标判定拓扑。

## 2. [P2] 地铁共线区段只把第一条线路写入寻路数据

位置：`scripts/process_osm.py:1005`。

地图绘制会遍历 `infos`，把共线的每条线都画出来。寻路导出却只写 `infos[0]`，即按名称排序后的第一条线。其余线路在共线区段丢失身份。

当前数据中，上海3号线和4号线的共线轨道只以3号线写入 `routing_metro.pkl`。“宜山路 → 海伦路”的路径因此变成3号线约12.996公里，再变成4号线约1.382公里。当前图还会免费切换线路，这又叠加了问题1。

影响：即使修复问题1，这里仍会让原本连续的线路出现缺段、虚假换乘或不必要绕行。港铁及轻铁的共线区段同样经过这条导出逻辑。

建议：为每条共线线路保留可遍历身份，可以采用物理边加线路集合。与问题1一起调整状态图，防止添加多线路后再次产生任意换乘。

## 3. [P2] 按地铁展示的市域和城际线路仍按国铁等级寻路

位置：`scripts/process_osm.py:708-710, 983-984`，消费位置：`scripts/build_graph.py:99-100`。

`routing_input.pkl` 在运营方归类后的图层生成之前导出，保留原始铁路等级。后来移入地铁图层的 `kind="m"` 线路又被 `if nm and not kind` 排除，不进入地铁寻路输入。结果是界面分类和寻路速度、站点匹配规则不一致。

当前输出的8条地铁运营线路均保留铁路等级，包括：

| 地图中的线路 | 寻路等级 | 当前名义速度 |
| --- | --- | --- |
| 市域铁机场联络线 | main | 100 km/h |
| 广清城际线、广肇城际线、广惠城际线、广州东环城际线、穗深城际线、琶莲城际线 | hsr200 | 160 km/h |
| 西户线 | branch | 60 km/h |

而 `metro` 的平均速度是36 km/h。铁路等级还使用铁路 hub 成本和铁路车站匹配规则。

影响：估算时间可能明显偏短。标为地铁站的站点不能直接挂到这些边，可能失去接入或只能通过另一个铁路站点绕行接入。这里没有声称36 km/h适合所有市域线路，问题是运营分类和寻路模型没有显式对齐。

建议：分开保存物理速度等级、运营类型和客运平均速度。对 `kind="m"` 的实际运营区段输出对应寻路属性，部分运营的线路不能把整条线都改成同一种类型。

## 4. [P2] 网络加载期间清除起终点会触发未捕获异常

位置：`src/app.html:1095-1096`。

`showRoute()` 在 `await loadNetwork()` 前检查了起终点，等待结束后直接读取可变的 `od.from.g` 和 `od.to.g`。等待期间点击清除，会把它们设为 `null`。

浏览器复现：将 `graph.json` 响应延迟2.5秒，选择“北京南 → 上海虹桥”，立即点击清除。随后发生：

```text
TypeError: Cannot read properties of null (reading 'g')
    at showRoute
```

建议：每次查询保存起终点快照，并使用递增请求序号使旧查询失效。等待结束后检查序号及当前状态。清除和交换起终点也应使之前的查询失效。

## 5. [P2] 修改站名后继续显示旧站点的路线

位置：`src/app.html:1192`。

输入事件只在输入框为空时清除已选站点。把一个已选站名修改为另一个非空名字时，内部 `od` 仍保留旧车站，已有路线也没有失效。

浏览器复现：先查询“北京南 → 上海虹桥”，页面显示京沪高铁、1,311公里、约4小时22分。把出发站输入框改为“广州南”，不点建议项，结果仍然是完全相同的京沪高铁路线。

影响：输入框和结果相互矛盾，用户可能把旧结果当成新查询结果。随后只改变另一个端点时，还会使用旧的内部出发站。

建议：输入文本一旦偏离已选站名，立即使该端点及路线失效，同时保留用户正在编辑的文本。不能直接调用会把输入框清空的现有 `setStop(role, null)`。

## 6. [P2] 结果列表会删除实际走过的具名线路

位置：`src/app.html:1135-1137`。

为了隐藏短接近线，代码按长度阈值过滤所有非地铁的具名路径段。它没有判断该段是否为必要连接，也没有保留被过滤段的换乘说明。

现有图复现：“成都东 → 重庆北”的原始路线依次经过：

1. 成渝高速线，296,207米。
2. 成渝高速渝贵联络线，1,798米。
3. 渝贵线，17,891米。
4. 沪蓉线，17,421米。

第2段低于2公里，被结果列表删除，但仍计入地图路径和总里程。“北京西 → 上海虹桥”也会隐藏实际走过的京哈线及京沪线短段。

建议：保留所有必要的具名线路。可把接近线折叠成可展开的说明，但不能让对外呈现的线路序列失去实际连接步骤。

## 7. [P2] 关闭铁路图层后，选中线路仍通过高亮层显示

位置：`src/app.html:1259-1272`。

`applyVisibility()` 控制基础线路层，遗漏 `hl`、`hl-core`、`hl-conv`、`hl-conv-core`、`hl-shared`、`hl-shared-core`。高亮层独立读取原始 source。

浏览器复现：在线路列表选中京沪高铁，再关闭350等级高铁开关。读取 MapLibre 状态：

```text
hsr350 visibility = none
hl visibility = visible（默认）
hl filter = ["==", ["get", "n"], "京沪高铁"]
```

影响：开关显示已关闭，但选中线路继续画出来。普速和共线的高亮层也存在同样遗漏。

建议：高亮层必须同时满足选中条件和分类可见条件，不能简单把全部高亮层绑定到“任一高铁可见”。共线高亮也要按自身等级过滤。

## 8. [P2] 同名站超过8个时，部分车站无法通过输入选择

位置：`src/app.html:1178-1180`。

搜索只匹配站名，不匹配城市，并固定截取前8项。相同完整站名的候选排序没有进一步的地域条件，也没有分页或展开。

当前可寻路数据有16个“奥体中心”、13个“会展中心”、9个“体育中心”。输入完整名字也只能看到前8项。继续输入无法区分同名站，输入城市也不会匹配，因为城市字段 `ct` 只用于展示。

影响：这些同名车站中排在后面的候选无法通过输入框选择，只能找到地图位置再点站。

建议：支持城市加站名的联合搜索，并为精确同名结果提供完整列表或分页。地图当前城市或距离可以参与排序，但排序不能代替完整可达的候选列表。

## 9. [P2] 原始数据缺失时仍成功覆盖已有提取缓存

位置：`scripts/extract_osm.py:44-47, 94-96`。

找不到必需的 `.osm.pbf` 时，代码仅打印 `missing` 并继续。最后仍以 `wb` 打开输出缓存，写入部分数据或空数据，进程成功结束。

隔离复现：提取原函数到临时目录，先创建一个含已有数据的 `extract.pkl`，再传入两份不存在的输入文件。原函数打印两个 `missing` 后写出：

```python
{'ways': [], 'stations': [], 'relations': [], 'places': []}
```

真实项目的原始文件和缓存没有被修改。这个问题可能在漏放台湾数据、输入文件改名或磁盘路径错误时导致下一轮生成丢失图层。

建议：开始读取前验证所有必需输入，缺失时以非零退出码终止。输出使用临时文件，成功完成和基本完整性检查后再原子替换已有缓存。

- 本地浏览器验证普通路线、站名编辑、延迟加载后清除、选中线路后关闭图层。

建议修复顺序：先处理1和2的线路状态图，然后对齐3的运营模型，再修4和5的查询状态，最后处理结果呈现、图层开关、搜索和提取失败保护。
